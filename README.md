# Парсер тематических чатов Telegram

Бот подключает Telegram-аккаунт, обходит его чаты и каналы и собирает
участников в базу без повторов. Пользователей без `@тега` пересылает
карточкой в отдельный канал, который создаёт сам.

Бот многопользовательский: у каждого свой подключённый аккаунт, свои
настройки, своя база и свои выгрузки. Данные разных пользователей не
пересекаются.

## Что делает

- Обходит все группы, супергруппы, форумы и каналы аккаунта.
- Видимость списка участников определяет по флагам `participants_hidden`
  и `can_view_participants` из `channelFull`, а не по тексту описания.
- Собирает авторов сообщений, авторов комментариев под постами каналов
  и, по желанию, список участников там, где он открыт.
- Дедуп глобальный: один человек — одна запись, сколько бы чатов его ни
  содержало.
- Идёт по истории до настраиваемой отсечки по времени, с чекпоинтами:
  прерванный прогон продолжается с того же места.
- Выгружает базу в XLSX, CSV, JSON и плоский список тегов.
- Позволяет добавлять теги вручную пачкой.

## Как устроена защита от ограничений

Обойти антиспам нельзя, но можно не попадать под его критерии.

**Разные ошибки лечатся по-разному.** `FloodWaitError` — обычный рейт-лимит
с числом секунд: короткий пересиживается, длинный прерывает прогон с
сохранением чекпоинта. `PeerFloodError` — не рейт-лимит, а поведенческая
пометка аккаунта, пересидеть её паузами нельзя: срабатывает circuit breaker,
прогон останавливается, аккаунт выводится из работы на сутки. Блокировка
лежит в БД, поэтому перезапуск процесса её не сбрасывает — иначе supervisor
поднимет бота, тот продолжит долбить, и временное ограничение станет
постоянным.

**Главный рычаг — какие методы вызываются.** `channels.getParticipants`
антиспам отслеживает: перебор ростера считается подготовкой к спаму.
`messages.getHistory` — обычное поведение любого клиента. Поэтому сбор по
истории включён по умолчанию, а перебор участников — нет.

**Ноль запросов на профили.** `username`, имя, `premium`, `bot`, `deleted`
приезжают в объекте `User` вместе с ответом `getHistory` или со списком
участников. `users.getFullUser` не вызывается ни разу: живой человек не
открывает десять тысяч профилей подряд.

**Ничего из «спамерского следа».** Ни `contacts.importContacts`, ни
`inviteToChannel`, ни `addChatUser`, ни отправки сообщений незнакомым.
`PeerFlood` прилетает в разы быстрее, когда сбор идёт в связке с этими
вызовами. Единственные операции записи — создать свой архивный канал и
переслать в него сообщение.

**Форма трафика.** Отдельные почасовые бюджеты по типам запросов на
токен-бакете: он пополняется непрерывно, поэтому вызовы размазываются по
часу вместо всплеска. Сверху случайная задержка — ровный интервал между
запросами сам по себе выглядит автоматом. Первые прогоны идут на четверти
бюджета, дальше разгон снимается.

**Комментарии одним проходом.** Они лежат в истории привязанной группы
обсуждений, поэтому читаются целиком за один обход вместо
`getDiscussionMessage` на каждый пост.

Чего это не даёт: потолок в 10 000 участников на чат серверный и не
обходится, уже случившийся `PeerFlood` программно не снимается, а гарантии
от ограничений не существует — Telegram правил не публикует.

## Установка

Нужны: сервер с Ubuntu/Debian, аккаунт Telegram и бот от @BotFather. Ключи
приложения заранее не нужны — бот получит их при подключении аккаунта.

### Через Docker

```bash
git clone <repo> /opt/tgparser
cd /opt/tgparser
sudo bash deploy/install.sh     # поставит docker и создаст .env с ключом
nano .env                       # заполнить BOT_TOKEN
docker compose up -d --build
docker compose logs -f
```

### Без Docker

```bash
git clone <repo> /opt/tgparser && cd /opt/tgparser
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
cp .env.example .env && chmod 600 .env
.venv/bin/python -m tgparser genkey   # значение в SESSION_ENCRYPTION_KEY
nano .env
.venv/bin/python -m tgparser check    # проверить конфигурацию
sudo cp deploy/tgparser.service /etc/systemd/system/
sudo systemctl enable --now tgparser
```

## Переменные окружения

| Переменная | Обязательна | Что это |
|---|---|---|
| `BOT_TOKEN` | да | Токен бота от @BotFather |
| `SESSION_ENCRYPTION_KEY` | да | Ключ шифрования сессий, `python -m tgparser genkey` |
| `API_ID`, `API_HASH` | нет | Общие ключи приложения по умолчанию |
| `ACCESS_MODE` | нет | `open` (по умолчанию) или `allowlist` |
| `ALLOWED_USER_IDS` | для `allowlist` | Список id через запятую |
| `ADMIN_ID` | нет | Кому доступна команда `/admin` со сводкой |
| `DB_PATH`, `EXPORT_DIR` | нет | Пути к базе и выгрузкам |
| `DEVICE_MODEL`, `SYSTEM_VERSION`, `APP_VERSION` | нет | Отпечаток клиента |
| `LOG_LEVEL` | нет | По умолчанию `INFO` |

## Ключи приложения

`api_id` и `api_hash` идентифицируют **приложение**, а номер с кодом —
**пользователя**. Порядок такой: программа сначала предъявляет серверу
`api_id` и получает право открыть соединение, и только внутри этого
соединения передаются номер и код. Telegram Desktop и мобильные клиенты
делают то же самое, просто их ключи вшиты внутрь и вы их не видите.

Метода для регистрации приложения в MTProto нет — Telegram отдаёт ключи
только через веб-форму на my.telegram.org. Но форма обычная, на сессионной
куке, поэтому бот проходит её сам: запрашивает код, логинится, создаёт
приложение и читает ключи. Замкнутый круг (код приходит внутрь Telegram, а
чтобы прочитать его программой, уже нужен `api_id`) разрывается тем, что код
вводит человек — тем же инлайн-падом.

Поэтому при подключении аккаунта бот предлагает три варианта: получить ключи
автоматически, ввести свои руками, либо взять общие из `.env`, если они там
заданы. Ключи, полученные для аккаунта, хранятся вместе с ним, а `api_hash`
шифруется тем же ключом, что и сессия.

**Автоматический путь работает не всегда.** Портал не рассчитан на
автоматические обращения и на серверные адреса регулярно отвечает безликой
ошибкой, особенно когда страна IP не совпадает со страной номера. В этом
случае бот показывает инструкцию и принимает ключи вручную:
my.telegram.org → вход по номеру → API development tools → любые поля →
Create application.

Свои ключи у каждого пользователя — это ещё и изоляция рисков. Telegram
выдаёт один `api_id` на номер, поэтому при открытом доступе ограничения,
полученные из-за чужого аккаунта, не бьют по остальным. Если задать общие
`API_ID` и `API_HASH` в `.env`, все аккаунты пойдут через один ключ, и
нарушения одного пользователя могут уронить бота для всех.

Публичные ключи из интернета не годятся: Telegram блокирует засвеченные, они
ловят `API_ID_PUBLISHED_FLOOD`.

## Работа

`/start` в боте → «Подключить аккаунт» → номер сообщением → откуда взять
ключи приложения → код.

Подключая аккаунт, пользователь отдаёт боту полный доступ к нему: сессия
хранится зашифрованной на сервере, где бот запущен. Бот предупреждает об
этом на экране ввода номера. Отключается кнопкой «Аккаунт», принудительно —
через «Устройства» в настройках Telegram.

### Два разных кода

В автоматическом получении ключей участвуют два кода, и они принимаются
по-разному — это не косметика, а следствие того, как Telegram их защищает.

**Код my.telegram.org** приходит буквенно-цифровым: `3QvmDbabncs`. В форме
портала поле для него называется `password`. Он принимается обычным
сообщением, и это безопасно: Telegram гасит только коды входа, а те
определены как последовательность из 5–7 десятичных цифр — буквенный код под
правило не попадает.

**Код входа в Telegram** состоит из цифр, и вот он гасится, если отправить
его сообщением внутри мессенджера: сервер сканирует сообщения от служебного
пользователя 777000 и вызывает `account.invalidateSignInCodes`. Поэтому он
набирается инлайн-клавиатурой — нажатие кнопки это callback query, а не
сообщение.

Код набирается инлайн-клавиатурой не для красоты: сервер Telegram гасит
коды, отправленные сообщением внутри мессенджера, — он сканирует сообщения
от служебного аккаунта 777000 на последовательность из 5–7 цифр. Нажатие
кнопки это callback query, а не сообщение, поэтому код остаётся живым.

Дальше «Запустить обход». Прогресс идёт в том же сообщении, сводка по
завершении дублируется в архивный канал. Прерванный прогон продолжается
кнопкой «Продолжить с места остановки».

## Настройки

Всё правится из бота: глубина истории, набор источников, пересылка
безтеговых, пропуск ботов, исключения топиков, бюджеты запросов в час.

Отдельно про форумы: история форум-группы читается одним проходом сразу по
всем топикам, поэтому ограничение самым активным топиком теряет людей без
экономии запросов. По умолчанию обходятся все топики за вычетом мусорных по
названию; переключатель на один топик есть в настройках.

## Разработка

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements-dev.txt
.venv/bin/python -m pytest        # 442 теста, сеть не нужна
.venv/bin/ruff check .
```

Тесты используют заглушку MTProto-слоя, повторяющую поведение настоящего
API, включая то, что `getHistory` возвращает авторов вместе с сообщениями.
Отдельный набор проверяет изоляцию между пользователями: чужие лиды,
аккаунты, настройки, чекпоинты и выгрузки не должны быть достижимы, в том
числе прямым обращением по id.

## Ограничения, о которых стоит знать заранее

Список участников супергруппы отдаётся максимум на 10 000 человек —
серверный лимит. У каналов подписчики не отдаются вообще, если вы не
администратор, поэтому по каналам собираются только комментаторы. Группы от
100 участников могут скрыть список участников целиком.

Пересылка сообщения сохраняет ссылку на автора не всегда: при настройке
«Пересланные сообщения → Никто» в карточке остаётся только имя без ссылки.
Такие записи помечаются флагом, и для них дополнительно хранится прямая
ссылка на исходное сообщение.

Сессия аккаунта в БД зашифрована, но потеря `SESSION_ENCRYPTION_KEY` делает
её нечитаемой — аккаунт придётся подключать заново.
